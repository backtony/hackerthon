# Feature workflow

## 공통 규칙

- 피처 문서와 Superpowers가 생성하는 문서는 `docs/feature-<name>/`에 둔다. `<name>`은 영문 kebab-case로 쓰며, Superpowers의 기본 `docs/superpowers/` 경로보다 우선한다.
- 설계·계획·구현 시 필요한 [개발가이드](../../../docs/개발가이드.md) 부분을 읽고 따른다.
- 시작하거나 재개할 때 기존 문서와 `Status`를 확인해 현재 단계부터 진행한다.
- `intent.md`, `spec-design.md`, `plan.md`, `verification.md`는 `Status: draft`로 작성하고 사용자의 명시적 승인 후 `Status: confirmed`로 바꾼다. 앞 단계가 확정되기 전에는 다음 단계로 진행하지 않는다. `question-<role>.md`와 선택적 `algorithm.md`는 별도 승인 단계가 없는 지원 문서다.
- 확정 문서를 수정하면 `draft`로 되돌리고 해당 단계부터 다시 승인받는다. `plan.md`의 작업 완료 표시만 바꾸는 경우는 제외한다. 문서와 코드가 다르면 기준을 명시하고 관련 문서를 먼저 갱신한다.
- 단순 변경은 문서 단계를 축약할 수 있지만, 이유와 검증 방법을 남긴다.
- 템플릿의 해당하지 않는 선택 항목과 빈 자리표시자는 산출물에서 제거한다.

## 단계

### 1. 의도 — `intent.md`

- 사용자에게 요구사항 URL 또는 문서를 입력받는다. 이미 제공됐다면 다시 요청하지 않고 원문을 읽는다. 접근할 수 없으면 내용을 요청한다.
- 원문을 바탕으로 [템플릿](assets/intent.md)에 문제, 영향받는 대상, 기대 결과를 기록하고 `출처`에 URL 또는 문서 경로를 남긴다. 구현 방법은 넣지 않는다.

### 2. 설계와 질의응답 — `spec-design.md`, `question-<role>.md`

- 확정된 `intent.md`와 `출처`(기존 문서의 `Sources` 포함)의 요구사항 원문을 함께 읽고 설계에 필요한 제약을 확인한다. 원문에 접근할 수 없으면 다시 요청하고, 확정된 의도와 충돌하면 사용자에게 확인한다.
- 이를 바탕으로 [템플릿](assets/spec-design.md)에 요구사항 ID별 수용 기준, 도메인·API·화면·데이터 설계, 대안과 트레이드오프를 `spec-design.md` 초안에 작성한다. 해당하지 않는 설계 항목은 만들지 않는다. 원문에 ID가 있으면 유지하고, 없으면 부여한다. 미확인 내용은 확정된 규칙처럼 쓰지 않는다.
- 답변할 직원 담당자·사용자 에이전트 등의 역할을 구분하고 [피처 인터뷰어 스킬](../feature-interviewer/SKILL.md)로 역할별 질답을 진행한다. 기존 피처에 `question.md`가 있다면 그 기록도 이어서 참고한다.
- 각 역할의 질문을 해소하고 역할 간 충돌을 정리한다. 새로 발견한 요구는 결정권자에게 채택 여부를 확인한다. 답을 얻지 못한 항목은 결정권자가 명시적으로 범위에서 제외한 경우에만 종료하고 제외 결정을 기록한다. 채택한 요구와 답변을 `spec-design.md` 초안에 반영한다.
- 갱신된 설계 초안을 기준으로, 알고리즘 선택이 필요한 요구사항은 [피처 알고리즘 스킬](../feature-algorithm/SKILL.md)로 조사·비교하고, 적합한 기존 방법이 없으면 설계한다. 이때만 `algorithm.md`를 만들고 개발자의 선택을 `spec-design.md`에 반영한다.
- 실제 요청·이벤트 흐름에서 동시성(다중 인스턴스 포함)과 데이터 정합성이 유지되는지 검토하고, 발생 가능한 위험에 맞는 방어 방식과 근거를 설계에 기록한다. 외부 의존성이 있다면 장애 시 동작과 필요한 보호 수단도 설계한다. 현재 `infrastructure:h2`는 스켈레톤 구성으로 보고 저장소·캐시·메시징 기술은 확정된 요구사항에 따라 선택하며, 필요한 어댑터·설정·실행 환경을 설계한다.
- 답변과 선택 결과를 반영한 `spec-design.md`를 검토받아 승인 시 확정한다. `intent.md`는 문제나 목표 자체가 달라진 경우에만 갱신한다.

### 3. 계획 — `plan.md`

- 확정된 `spec-design.md`를 계획의 기준으로 삼는다. 결정 근거가 필요하면 `intent.md`, `question-<role>.md`(기존 `question.md` 포함), `algorithm.md`를 참고하고, 계획에 필요한 내용이 빠졌거나 충돌하면 설계를 보완해 다시 승인받는다.
- `superpowers:writing-plans`로 설계를 정확한 모듈·파일, 영향받는 인터페이스, 작업 간 선행 관계와 수정 파일 범위, 요구사항 ID별 검증 기준·명령과 완료 조건으로 분해해 [템플릿](assets/plan.md)에 기록한다. 독립 작업은 병렬 실행할 수 있게 표시한다. 이 워크플로에서는 해당 스킬의 필수 실행 스킬 헤더와 작업별 TDD·커밋 형식을 적용하지 않는다.
- 선택한 기술에 필요한 모듈 등록·Gradle 의존성·설정·서버 조합·검증 환경을 해당 작업에 포함한다.
- 테스트는 개발가이드의 테스트 관례에 따라 회귀 방지 가치가 있는 동작에만 계획한다. 별도 테스트가 불필요한 작업에는 TDD 단계를 넣지 않고 빌드·정적 검증으로 확인한다.
- 계획 승인 요청에서 4단계 작업이 작고 계획이 명확하며 보안·데이터·통합 위험이 낮으면 더 가벼운 모델로도 충분한지 판단해 한 번 권고한다. 모델 전환은 사용자가 선택하며, 별도 요청이 없으면 현재 모델로 진행한다.

### 4. 구현

- 확정된 `plan.md`에서 선행 관계가 없고 수정 파일·공유 자원이 겹치지 않는 작업은 `superpowers:dispatching-parallel-agents`로 동시에 구현한다. 서로 의존하거나 같은 파일을 수정하는 작업은 순서대로 진행한다. 병렬 실행 도구가 없으면 직접 구현한다.
- 주 에이전트가 각 작업의 결과를 확인하고 변경사항을 통합해 검증한 뒤 `plan.md`에 완료 상태를 표시한다. 하위 에이전트는 `plan.md`를 수정하지 않는다.

### 5. 검증 — `verification.md`

- 구현 후 [템플릿](assets/verification.md)으로 `verification.md`를 작성한다. 보안·데이터 무결성·복잡한 통합 등 회귀 영향이 큰 변경에서만, 사용할 수 있으면 검증 에이전트에 독립 검증을 맡긴다. 나머지는 구현 단계와 분리된 검증 패스로 진행한다. 두 경우 모두 요구사항 ID별 구현, 설계한 동시성·정합성·장애 대응, 엣지 케이스, 보안·통합 영향, 회귀 위험, 변경 diff, fresh command 결과와 잔여 위험을 확인해 기록한다.
- 문제가 발견되면 `verification.md`에 미완료로 기록한다. 기존 작업의 완료 조건이 깨졌다면 `plan.md`의 해당 완료 표시를 해제하고, 별개 문제라면 수정 작업을 계획에 추가한다. 설계 변경이 필요하면 `spec-design.md`부터 갱신해 승인받는다. 수정 후 다시 검증한다.
- 테스트 통과만으로 완료를 주장하지 않고 `superpowers:verification-before-completion`을 적용한다.
